# মাইগ্রেশন যাচাই — লোকাল Postgres

এই প্রজেক্টের মাইগ্রেশন হাতে চালানো হয় Supabase SQL এডিটরে। অর্থাৎ কোনো
মাইগ্রেশন ফাইল **একজন মানুষ চালানোর আগে কখনো চলে না** — আর যে ফাইল কখনো চলেনি,
সেটা কোড নয়, অনুমান। এই ফোল্ডারটা অনুমানটাকে ফলাফলে বদলায়।

```bash
bash supabase/tests/run-local-checks.sh
# অন্য কোনো মাইগ্রেশন হলে:
bash supabase/tests/run-local-checks.sh supabase/migrations/2026XXXX_....sql

# Sprint 5 — কর্মঘণ্টা, ছুটি, রিশিডিউল, রিমাইন্ডার (৫৪টা চেক)
bash supabase/tests/run-sprint5-checks.sh

# Sprint 5.1 হার্ডেনিং — অ্যাপয়েন্টমেন্ট টাকার হিসাবে (৭৮টা চেক)
bash supabase/tests/run-sprint5-hardening-checks.sh

# Sprint 6 — মেম্বারশিপ (১২১টা চেক)
bash supabase/tests/run-sprint6-checks.sh

# Sprint 7 — লয়্যালটি পয়েন্ট (১১০টা চেক)
bash supabase/tests/run-sprint7-checks.sh

# Sprint 8 — রেফারেল (২১৭টা চেক)
bash supabase/tests/run-sprint8-checks.sh
```

স্ক্রিপ্টটা একটা **অস্থায়ী লোকাল Postgres ক্লাস্টার** বানায়, `fixture.sql` দিয়ে
আসল স্কিমার প্রয়োজনীয় অংশটুকু (shops, chairs, services, profiles,
chair_service_stats, `auth.uid()`, `is_shop_owner()`) দাঁড় করায়, তারপর আসল
মাইগ্রেশন ফাইলটা চালায় — শেষে ক্লাস্টারটা মুছে ফেলে।

**কোনো Supabase প্রজেক্ট স্পর্শ করে না।**

## কী কী যাচাই হয়

| ধাপ | কী দেখে |
|---|---|
| গঠন | RLS চালু, পলিসির সংখ্যা, কনস্ট্রেইন্ট, ইনডেক্স, RPC-র SECURITY মোড |
| ইনসার্ট ট্রিগার | `ends_at` সার্ভার হিসাব করে, দাম জমাট, অতীত/ক্রস-শপ/সময়ের বাইরে reject |
| স্ট্যাটাস মেশিন | অবৈধ ট্রানজিশন reject, DONE চূড়ান্ত, ইতিহাস পুনর্লিখন অসম্ভব |
| আইসোলেশন | **আসল non-superuser রোলে** — অন্য দোকানের মালিক ০ সারি দেখে |
| স্লট RPC | বুকিং করলে ওভারল্যাপিং স্লট সরে, বাতিল করলে ফিরে আসে |
| কনকারেন্সি | ৮টা সমান্তরাল ক্লায়েন্ট একই স্লট চায় → ঠিক ১টা টেকে |

হার্ডেনিং স্ক্রিপ্টটা (`run-sprint5-hardening-checks.sh`) বাড়তি যা দেখে:

| ধাপ | কী দেখে |
|---|---|
| `completed_at` | DONE-এ বসে, IN_PROGRESS-এ বসে না, একবার বসলে আর সরে না |
| ঐতিহাসিক দাম | সার্ভিসের রেট বদলালেও পুরনো অ্যাপয়েন্টমেন্টের দাম/স্ন্যাপশট অপরিবর্তিত |
| টাকার সম্পর্ক | অ্যাপের তিনটে কোয়েরি (ইনকাম, ক্যাশবুক, বাকির খাতা) হুবহু SQL হিসেবে |
| লিস্ট ফিল্টার | today / upcoming / completed / cancelled / provider / তারিখ-রেঞ্জ |
| আইসোলেশন | **আসল non-superuser রোলে** — B-এর আয়ে A-র এক টাকাও নেই |
| বকেয়া রিমাইন্ডার | মালিক-চেক, ২৪ ঘণ্টার কুলডাউন, বাকি-নেই, অ্যাকাউন্ট-নেই |
| সেলুন রিগ্রেশন | `serials` টেবিল, তার ট্রিগার, `send_due_reminder`, `total_amount` লেখা — সব আগের মতো |

সেলুন রিগ্রেশনের জন্য স্ক্রিপ্টটা নিজেই একটা ছোট `serials` টেবিল বানায় (শেয়ার্ড
`fixture.sql`-এ নয়, কারণ বাকি দুটো স্ক্রিপ্টের ওটা লাগে না) — যাতে "কিউ আগের
মতোই চলে" কথাটা একটা আসল সারিতে প্রমাণ হয়, অনুপস্থিত টেবিল নিয়ে দাবি না হয়।

Sprint 6-এর স্ক্রিপ্টটা (`run-sprint6-checks.sh`) দেখে:

| ধাপ | কী দেখে |
|---|---|
| গঠন | দুটো টেবিল, RLS, ২+৫ পলিসি, **DELETE পলিসি নেই**, পার্শিয়াল ইউনিক ইনডেক্স, ট্রিগার, ফাংশনের SECURITY মোড |
| টিয়ার | দাম/মেয়াদ/নামের বাউন্ড, প্রতি-দোকানে নাম ইউনিক, বেনিফিটের আকৃতি (৫টা কেস) |
| এনরোলমেন্ট | **সার্ভারই দাম ঠিক করে** — ক্লায়েন্টের পাঠানো দাম/মেয়াদ/স্ন্যাপশট ওভাররাইট হয়; ক্রস-শপ ও নিষ্ক্রিয় টিয়ার reject |
| এক জীবিত সদস্যপদ | দ্বিতীয়টা reject, অন্য দোকানে ঠিক আছে, বাতিলের পর আবার নেওয়া যায় |
| লাইফসাইকেল | স্ট্যাটাস মেশিন, স্ট্যাম্প, **মেয়াদের জানালা পরে বাড়ানো যায় না** |
| মেয়াদ | cron না চললেও মেয়াদোত্তীর্ণ সদস্যপদ "চালু" নয়; নবায়ন আটকায় না |
| ইতিহাস | টিয়ার এডিট করেও পুরনো সদস্যপদের দাম/নাম/মেয়াদ/বেনিফিট অপরিবর্তিত |
| আইসোলেশন | **আসল non-superuser রোলে** — পড়া ও লেখা দুদিকেই, মালিক ও কাস্টমার দুপক্ষের জন্য |
| রিগ্রেশন | সিরিয়াল, অ্যাপয়েন্টমেন্ট, তাদের টাকা — সব অপরিবর্তিত; মেম্বারশিপের টাকা ওদের আয়ে মেশে না |

**একটা আসল ফাঁক এই স্ক্রিপ্টই ধরেছে:** RLS কাস্টমারকে PENDING সারি বানাতে দেয়,
আর প্রথম ড্রাফটে কিছুই তাকে ওই একই ইনসার্টে `payment_status='PAID'` পাঠানো থেকে
আটকাত না — অর্থাৎ নিজের টাকা দেওয়ার নিজেই সাক্ষী। এখন ট্রিগার মালিক ছাড়া সবার
জন্য টাকার কলামগুলো জোর করে DUE করে দেয় (ইনসার্ট ও আপডেট, দুটোতেই)।

Sprint 7-এর স্ক্রিপ্টটা (`run-sprint7-checks.sh`) দেখে:

| ধাপ | কী দেখে |
|---|---|
| গঠন | তিনটে টেবিল, RLS, আর **লেখার পলিসির অনুপস্থিতি** — accounts/ledger-এ ঠিক ১টা করে SELECT পলিসি, কোনো INSERT/UPDATE/DELETE নেই (সিদ্ধান্ত ৩২) |
| PK | `loyalty_accounts`-এর প্রাইমারি কী সত্যিই `(shop_id, customer_id)` (সিদ্ধান্ত ৩৩) |
| সূত্র | `points_for_bill` — floor, min_bill, শূন্য-হার, null, ৯টা কেস |
| জমা | সিরিয়াল থেকে **আর** অ্যাপয়েন্টমেন্ট থেকে, স্ন্যাপশটসহ (বিল + হার) |
| দুবার নয় | একই কাজে দ্বিতীয়বার `unique_violation`; DONE সারির পরের আপডেটে কিছুই বসে না |
| সুইচ | `is_enabled=false` হলে কাজ শেষ হলেও কিছুই জমে না, অথচ কাজটা স্বাভাবিকভাবেই শেষ হয় |
| ইনভ্যারিয়েন্ট | **ব্যালেন্স = লেজারের যোগফল**, সংশোধনের আগে ও পরে |
| আইসোলেশন | প্ল্যানের তিনটে নামধারী টেস্ট — (ক) B মালিক A-র অ্যাকাউন্ট পড়তে পারে না · (খ) কাস্টমার (আর মালিকও) সরাসরি ব্যালেন্স UPDATE করতে পারে না · (গ) অন্য দোকানের `shop_id` দিয়ে `loyalty_award` ব্যর্থ হয় |
| রিগ্রেশন | পাঁচটা বিদ্যমান ট্রিগার, ওভারল্যাপ কনস্ট্রেইন্ট, মেম্বারশিপ পলিসি, দুই পাশের আয়ের কোয়েরি — সব অপরিবর্তিত |
| ব্যর্থতা-সহনশীলতা | লেজার ইনসার্ট ভেঙে দিয়ে দেখা হয়: **DONE ট্রানজিশন তখনো সফল**, আর আংশিক পয়েন্টও বসে না |

**এই স্ক্রিপ্টে দুটো জিনিস ইচ্ছাকৃতভাবে কঠিন।** এক, লয়্যালটির লেখা ভাঙার
জন্য `check (false) not valid` ব্যবহার করা হয় — সাধারণ `add constraint`
নিজের টেবিল-স্ক্যানেই ব্যর্থ হতো, ফলে কিছুই ভাঙত না আর টেস্টটা মিথ্যে পাস
দিত (প্রথম রানে ঠিক এটাই হয়েছিল)। দুই, প্রতিটা লেখার চেষ্টা `app_user`
রোলে চলে, কারণ superuser RLS বাইপাস করে **আর** তার `auth.uid()` নেই, অথচ
প্রতিটা লয়্যালটি RPC `is_shop_owner()` দেখে।

Sprint 8-এর স্ক্রিপ্টটা (`run-sprint8-checks.sh`) দেখে:

| ধাপ | কী দেখে |
|---|---|
| গঠন | দুটো টেবিল, RLS, আর **লেখার পলিসির অনুপস্থিতি** — দুটোতেই ঠিক ১টা করে SELECT পলিসি; PK `(shop_id, customer_id)`, কম্পোজিট FK, কনভার্সন-শেপ CHECK, ইতিহাস-জমাট ট্রিগার |
| সমান্তরাল কিছু নেই | `referral_rewards`/`referral_points`/`referral_accounts`/`referral_transactions` — **চারটেরই অনুপস্থিতি**; লেজারের `kind` বেড়েছে, পুরনো তিনটে মান এখনো বৈধ |
| সুইচ | লয়্যালটি একা, রেফারেল একা — কোনোটাই যথেষ্ট নয়; **দুটো একসাথে** লাগে |
| কোড | একবারই তৈরি, দ্বিতীয় কল একই কোড; এক কাস্টমারের দুই দোকানে **দুটো আলাদা** কোড; কোডে `0/1/I/L/O` নেই; ভ্যানিটি কোড বসানো যায় না |
| দাবি | খালি · অজানা · নিজের · **অন্য দোকানের** (দুই দিকেই) · দ্বিতীয়বার · "দেরি হয়ে গেছে" — ছয়টা refuse |
| **পুরস্কার নয়** | বৈধ দাবির পরেও **০টা লেজার সারি, ০টা অ্যাকাউন্ট** — কোড লিখলেই কিছু জমে না |
| রূপান্তর | অ্যাপয়েন্টমেন্ট থেকে **আর** সিরিয়াল থেকে; দুই পাশের পয়েন্ট, স্ন্যাপশটসহ; লয়্যালটি আগে বসে, রেফারেল বোনাস তার পরে |
| দুবার নয় | দ্বিতীয় কাজে বোনাস নয়; `referral_convert` আবার ডাকলে ০; `referral_award_points` আবার ডাকলে `duplicate key` |
| ক্রস-শপ | B দোকানের পুরস্কার A দোকানে **এক পয়েন্টও** দেয় না; কোনো লেজার সারি শপ পার হয় না |
| জালিয়াতি | জাল রেফারেল, জাল `CONVERTED` সারি, অন্যের নামে রেফারার — তিনটেই RLS-এ আটকায়; মালিকও সরাসরি `CONVERTED` করতে পারে না; converted সারি un-convert করা যায় না |
| মালিকের সীমা | `shop_referral_stats`/`referral_convert`/`referral_award_points` অন্য দোকানে `not your shop`; কাস্টমারও নিজেকে পুরস্কার দিতে পারে না |
| ইনভ্যারিয়েন্ট | **ব্যালেন্স = লেজারের যোগফল**, প্রতিটা ধাপে; প্রতিটা রেফারেল-সারি ওই রেফারেলের কোনো এক পক্ষের |
| ব্যর্থতা-সহনশীলতা | লেজারের রেফারেল-ইনসার্ট ভেঙে দিয়ে দেখা হয়: **DONE সফল**, কাজের নিজের পয়েন্ট বসে, রেফারেল **PENDING-ই থাকে** (রূপান্তর পুরোটা ফিরে যায়), আর পরের কাজে ঠিকই রূপান্তরিত হয় |
| রিগ্রেশন | সেলুন, অ্যাপয়েন্টমেন্ট, মেম্বারশিপ, লয়্যালটি — ট্রিগার, পলিসি, ফাংশন, দুই পাশের আয়ের কোয়েরি, সব অপরিবর্তিত; `loyalty_award`-এর কোনো overload তৈরি হয়নি |

**এই স্ক্রিপ্টের সবচেয়ে গুরুত্বপূর্ণ চেকটা একটা "কিছুই হয়নি" চেক:** বৈধ দাবির
ঠিক পরে `select count(*) from loyalty_transactions` **০** হতে হবে। কোড লিখলেই
পয়েন্ট বসে গেলে পুরো ফিচারটা একটা পয়েন্টের কল হয়ে যেত, আর সেটা একটা
পাসিং স্ট্রাকচারাল টেস্টের নিচে সহজেই লুকিয়ে থাকতে পারত।

আইসোলেশনের ধাপটা `app_user` নামে একটা আলাদা রোল বানিয়ে চালায়, কারণ
**superuser আর টেবিলের মালিক RLS বাইপাস করে** — postgres ইউজারে পরীক্ষা করলে
সব পলিসি "পাস" দেখাত, অথচ কিছুই প্রমাণ হতো না।

## দরকার

- `postgresql-16` বাইনারি (`/usr/lib/postgresql/16/bin`)
- একটা non-root ইউজার — Postgres root হিসেবে চলতে অস্বীকার করে।
  ডিফল্ট `postgres`; বদলাতে `RUNAS=youruser bash ...`

## সীমা — যা এটা প্রমাণ করে না

লোকাল ক্লাস্টার ≠ তোমার Supabase ইনস্ট্যান্স। ফিক্সচারটা আসল স্কিমার **নকল**,
হুবহু কপি নয় — বাস্তব টেবিলে বাড়তি কলাম, ট্রিগার বা পলিসি আছে যা এখানে নেই।
তাই এটা পাস করা মানে "মাইগ্রেশনটা যুক্তিতে ঠিক", **"তোমার ডেটাবেসে চলবে" নয়**।
আসল যাচাই এখনো SQL এডিটরে ফাইলের শেষের ভেরিফিকেশন ব্লক চালানো।
