**এগারোটা একসাথে: ৪০ · ৫৪ · ৭৯ · ১২১ · ১১০ · ২১৭ · ২০৪ · ১৯৪ · ৪৩ · ৬১ · ৭৫ = ১১৯৮টা চেক।**

পলিশ হার্নেসটা দুটো মাইগ্রেশন যাচাই করে (`20260928`, `20260929`), আর তার সবচেয়ে
জরুরি অংশটা ইতিহাস নিয়ে: কাস্টমারের বাছা স্টাইলের নাম **catalogue-এ নাম বদলালেও
বদলায় না**, আর **স্টাইল পুরো মুছে দিলেও সারিটা টেকে**। "সংরক্ষিত থাকে" দাবিটা
ধ্বংসাত্মক এডিটের *পরে* কী হয় তার দাবি, তাই হার্নেস এডিটটা সত্যিই করে দেখে।
এটা `hairstyles`/`serial_style_preferences` বানাতে **আসল `20260914`** চালায়, আর
Supabase-এর মতো `anon`/`authenticated`/`service_role` রোল দাঁড় করিয়ে
**`authenticated` হিসেবেই** সব আইসোলেশন চেক করে।

`run-sprint11-audit-checks.sh` বাকিগুলোর থেকে আলাদা, আর সেটা ইচ্ছাকৃত। অন্য সব হার্নেস একটা মাইগ্রেশনের DDL
পরীক্ষা করে; এটা পরীক্ষা করে **একটা GRANT**। grant ফাংশনের বডি চেনে না, তাই ফিক্সচারে
সতেরোটা ফাংশন এক লাইনের stub হিসেবে বসে — হুবহু একই signature নিয়ে — আর তার উপর আসল
`20260927_function_grants.sql` চলে। যেটা ফিক্সচারকে বিশ্বস্তভাবে নকল করতে **হয়**, সেটা
privilege environment: Postgres নতুন ফাংশন PUBLIC-কে দেয়, আর Supabase DEFAULT PRIVILEGES
দিয়ে `anon`/`authenticated`-কে **নাম ধরে**ও দেয়। দ্বিতীয়টাই ফাঁদ — শুধু PUBLIC থেকে revoke
করলে বেয়ার ক্লাস্টারে কাজ হয়েছে মনে হয় আর Supabase-এ কিছুই বদলায় না। তাই হার্নেস দুটোই
বসায়, আর একটা চেক (`aclexplode` দিয়ে) শুধু এটা প্রমাণ করতেই আছে যে নাম-ধরে-দেওয়া grant
সত্যিই ছিল — নইলে “পরে”র চেকগুলো ভুল কারণে পাস করত।

এই ফোল্ডারের বাইরে আরেকটা যাচাই আছে, আর ওটা ডেটাবেসের নয় — **ব্রাউজারের**:

```bash
npx next dev -p 3111 &                 # প্লেসহোল্ডার Supabase env-এই চলে
npm i --no-save playwright@1.49.1      # ইচ্ছাকৃতভাবে dependency নয়
node scripts/verify-browser.mjs        # ৬৪টা চেক, আসল Chromium-এ
```

Sprint 11-এ প্রথমবার ব্রাউজার যাচাই সত্যিই চালানো হয়েছে। যা যাচাই হয় তা
**সেশন ছাড়া যা যাচাই করা সম্ভব** — পাবলিক পর্দা (`/`, `/login`, `/register`),
পুরো থিম সিস্টেম, ৩২০px লেআউট (`/explore` সহ) আর চারটে প্যালেটের কনট্রাস্ট। লগইন-পরবর্তী
পর্দাগুলো **যাচাই হয় না**, কারণ তার জন্য আসল Supabase ক্রেডেনশিয়াল দরকার —
সেটা অনুমান করার বদলে রিপোর্টে “হয়নি” লেখা থাকে।

স্ক্রিপ্টটা একটা **অস্থায়ী লোকাল Postgres ক্লাস্টার** বানায়, `fixture.sql` দিয়ে
আসল স্কিমার প্রয়োজনীয় অংশটুকু (shops, chairs, services, profiles,
chair_service_stats, `auth.uid()`, `is_shop_owner()`) দাঁড় করায়, তারপর আসল
মাইগ্রেশন ফাইলটা চালায় — শেষে ক্লাস্টারটা মুছে ফেলে।

**কোনো Supabase প্রজেক্ট স্পর্শ করে না।**

## কী কী যাচাই হয়

| ধাপ | কী দেখে |
|---|---|
| গঠন | RLS চালু, পলিসির সংখ্যা, কনস্ট্রেইন্ট, ইনডেক্স, RPC-র SECURITY মোড |
| ইনসার্ট ট্রিগার | `ends_at` সার্ভার হিসাব করে, দাম জমাট, অতীত/ক্রস-শপ/সময়ের বাইরে reject |
| স্ট্যাটাস মেশিন | অবৈধ ট্রানজিশন reject, DONE চূড়ান্ত, ইতিহাস পুনর্লিখন অসম্ভব |
| আইসোলেশন | **আসল non-superuser রোলে** — অন্য দোকানের মালিক ০ সারি দেখে |
| স্লট RPC | বুকিং করলে ওভারল্যাপিং স্লট সরে, বাতিল করলে ফিরে আসে |
| কনকারেন্সি | ৮টা সমান্তরাল ক্লায়েন্ট একই স্লট চায় → ঠিক ১টা টেকে |

হার্ডেনিং স্ক্রিপ্টটা (`run-sprint5-hardening-checks.sh`) বাড়তি যা দেখে:

| ধাপ | কী দেখে |
|---|---|
| `completed_at` | DONE-এ বসে, IN_PROGRESS-এ বসে না, একবার বসলে আর সরে না |
| ঐতিহাসিক দাম | সার্ভিসের রেট বদলালেও পুরনো অ্যাপয়েন্টমেন্টের দাম/স্ন্যাপশট অপরিবর্তিত |
| টাকার সম্পর্ক | অ্যাপের তিনটে কোয়েরি (ইনকাম, ক্যাশবুক, বাকির খাতা) হুবহু SQL হিসেবে |
| লিস্ট ফিল্টার | today / upcoming / completed / cancelled / provider / তারিখ-রেঞ্জ |
| আইসোলেশন | **আসল non-superuser রোলে** — B-এর আয়ে A-র এক টাকাও নেই |
| বকেয়া রিমাইন্ডার | মালিক-চেক, ২৪ ঘণ্টার কুলডাউন, বাকি-নেই, অ্যাকাউন্ট-নেই |
| সেলুন রিগ্রেশন | `serials` টেবিল, তার ট্রিগার, `send_due_reminder`, `total_amount` লেখা — সব আগের মতো |

সেলুন রিগ্রেশনের জন্য স্ক্রিপ্টটা নিজেই একটা ছোট `serials` টেবিল বানায় (শেয়ার্ড
`fixture.sql`-এ নয়, কারণ বাকি দুটো স্ক্রিপ্টের ওটা লাগে না) — যাতে "কিউ আগের
মতোই চলে" কথাটা একটা আসল সারিতে প্রমাণ হয়, অনুপস্থিত টেবিল নিয়ে দাবি না হয়।

| ধাপ | কী দেখে |

| লাইফসাইকেল | স্ট্যাটাস মেশিন, স্ট্যাম্প, **মেয়াদের জানালা পরে বাড়ানো যায় না** |
| মেয়াদ | cron না চললেও মেয়াদোত্তীর্ণ সদস্যপদ "চালু" নয়; নবায়ন আটকায় না |
| ইতিহাস | টিয়ার এডিট করেও পুরনো সদস্যপদের দাম/নাম/মেয়াদ/বেনিফিট অপরিবর্তিত |

| রিগ্রেশন | সিরিয়াল, অ্যাপয়েন্টমেন্ট, তাদের টাকা — সব অপরিবর্তিত; মেম্বারশিপের টাকা ওদের আয়ে মেশে না |

**একটা আসল ফাঁক এই স্ক্রিপ্টই ধরেছে:** RLS কাস্টমারকে PENDING সারি বানাতে দেয়,
আর প্রথম ড্রাফটে কিছুই তাকে ওই একই ইনসার্টে `payment_status='PAID'` পাঠানো থেকে
আটকাত না — অর্থাৎ নিজের টাকা দেওয়ার নিজেই সাক্ষী। এখন ট্রিগার মালিক ছাড়া সবার
জন্য টাকার কলামগুলো জোর করে DUE করে দেয় (ইনসার্ট ও আপডেট, দুটোতেই)।

দিত (প্রথম রানে ঠিক এটাই হয়েছিল)। দুই, প্রতিটা লেখার চেষ্টা `app_user`

**এই স্ক্রিপ্টের সবচেয়ে বলার মতো চেকটা একটা `null` চেক।** একটা সিটের
`staff_working_hours` ইচ্ছা করে **মুছে** দেওয়া হয় (`chairs_seed_staff_hours`
ট্রিগার দুটো সিটকেই সময়সূচি দিয়ে দিয়েছিল, তাই অবস্থাটা তৈরি করতে হয়েছে), আর
তারপর অ্যাসার্ট করা হয় যে ওর ব্যবহার **`null`, ০ নয়** — কারণ "কোনো কাজ করেনি"
আর "কত সময় দিয়েছিল জানা নেই" দুটো আলাদা সত্য, আর দ্বিতীয়টাকে ০% দেখালে
ড্যাশবোর্ডটা মিথ্যে বলত।

Sprint 11-এর স্ক্রিপ্টটা (`run-sprint11-checks.sh`) দেখে:

| ধাপ | কী দেখে |
|---|---|
| গঠন | কলামটা আছে, `text` (enum নয়), **nullable ও ডিফল্ট ছাড়া**, CHECK আছে আর তাতে `UNISEX` নেই; কোনো সমান্তরাল প্রেফারেন্স টেবিল তৈরি হয়নি; **ডেটাবেসে একটাও `theme` কলাম নেই** |

**এই স্ক্রিপ্টের সবচেয়ে গুরুত্বপূর্ণ ধরনের চেকটা একটা *নীরব* ব্যর্থতার চেক।**
RLS-এ আটকানো একটা UPDATE **কোনো এরর দেয় না** — পলিসির USING ক্লজ সারিটাই
দেখতে দেয় না, তাই ০টা সারি বদলায় আর psql বলে `UPDATE 0`। Sprint 8 এটা কষ্ট
করে শিখেছিল, তাই এখানে অ্যাসারশনটা এররের উপর নয়, **মানের উপর**: B চেষ্টা
করার পরেও A-র পছন্দ যা ছিল তাই আছে।

**একটা জিনিস ইচ্ছাকৃতভাবে *সর্বজনীন*।** ব্রিফ বলেছিল "Shop A cannot read
Shop B rewards"। চালু দোকানের **চালু** ক্যাটালগটা সবাই পড়তে পারে — পারতে
হবেই, নইলে কাস্টমার শেলফটা দেখতে পাবে না (`membership_tiers`-এর
"browse active" আর `offers`-এর একই নকশা)। যা সত্যিই গোপন, আর যা এই স্ক্রিপ্ট
নামধারী চেকে প্রমাণ করে: **বন্ধ** ক্যাটালগ, আর **প্রতিটা রিডেম্পশন**।

আইসোলেশনের ধাপটা `app_user` নামে একটা আলাদা রোল বানিয়ে চালায়, কারণ
**superuser আর টেবিলের মালিক RLS বাইপাস করে** — postgres ইউজারে পরীক্ষা করলে
সব পলিসি "পাস" দেখাত, অথচ কিছুই প্রমাণ হতো না।

## সীমা — যা এটা প্রমাণ করে না

লোকাল ক্লাস্টার ≠ তোমার Supabase ইনস্ট্যান্স। ফিক্সচারটা আসল স্কিমার **নকল**,
হুবহু কপি নয় — বাস্তব টেবিলে বাড়তি কলাম, ট্রিগার বা পলিসি আছে যা এখানে নেই।
তাই এটা পাস করা মানে "মাইগ্রেশনটা যুক্তিতে ঠিক", **"তোমার ডেটাবেসে চলবে" নয়**।
আসল যাচাই এখনো SQL এডিটরে ফাইলের শেষের ভেরিফিকেশন ব্লক চালানো।
